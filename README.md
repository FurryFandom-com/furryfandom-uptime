## What is monitored

| Component      | What it covers                                              |
| -------------- | ----------------------------------------------------------- |
| Website        | The main site at furryfandom.com                            |
| API            | The application behind the site                             |
| Messenger      | The messenger at messenger.furryfandom.com                  |
| Real-time chat | The live connection that delivers messages as they are sent |

Checks run every five minutes. Response times are recorded over time and
charted on the status page.

FurryFandom also depends on services it does not operate — payments run through
Stripe, and traffic is served through Cloudflare. Those can be degraded while
every check here is green, so both are linked from the status page.

## Why this is a separate repository

A status page is only worth having if it survives the thing it reports on.
These checks run on GitHub's infrastructure, entirely separate from the systems
being monitored, so an outage cannot take the status page down with it.

**That independence is the whole design, and it is easy to break.** These
workflows must keep running on GitHub-hosted runners. Moving them onto any
infrastructure that shares failure modes with the services being monitored —
however convenient — would mean the monitor goes dark in exactly the incidents
it exists to report.

## Why the workflows are hand-edited

Every job declares the narrowest set of permissions it needs rather than relying
on broad defaults:

```yaml
permissions:
  contents: write
  issues: write
```

Two of Upptime's workflows cannot work within that and were **removed** rather
than granted more:

| Removed               | What it did                                                | Why it is gone                                                                                                                             |
| --------------------- | ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| `update-template.yml` | Weekly sync of `.github/workflows/*` from upstream Upptime | Rewriting workflow files requires `workflows: write`, which would let an upstream repository push arbitrary workflow changes into this one |
| `updates.yml`         | Ran `upptime/updates@master` to self-update the repo       | Same permission, plus an unpinned third-party action running with write access                                                             |

The `update-template` step was dropped from `setup.yml` for the same reason, and
`.templaterc.json` is left at `{"files": []}` as a second line of defence if
anyone restores those workflows.

**The consequence is that the workflows are pinned.** Upstream Upptime changes
no longer arrive on their own, and the `upptime/uptime-monitor` version has to be
bumped by hand. Editing `workflowSchedule` in `.upptimerc.yml` will not change
the cron expressions either — edit the workflow files directly. For a status
page, predictability is worth more than auto-updates.

To take upstream updates automatically instead: create a fine-grained PAT scoped
to this repository only (Contents, Issues and Workflows read/write), store it as
the `GH_PAT` secret, restore the two workflows from
[upptime/upptime](https://github.com/upptime/upptime), and set `.templaterc.json`
back to `{"files": [".github/**/*"]}`. Every workflow already prefers
`secrets.GH_PAT` over `github.token` when it exists.

## Operating it

- **Incidents** open and close automatically as issues in this repository,
  assigned to the `assignees` list in `.upptimerc.yml`. Commenting on an open
  incident publishes that comment to the status page, which is how to post a
  human explanation during an outage.
- **Maintenance windows** use the "Maintenance event" issue template.
- **Changing what is monitored** means editing `.upptimerc.yml` only. Pushing it
  triggers `Setup CI`, which regenerates the status page — but never hand-edit
  the workflow files' generated headers, and see the pinning note above.
